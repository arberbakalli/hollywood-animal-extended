## Mistakes

1. **A test of a symptom, not the defect.** TC35-000008 checked overflow; the
   real defect (a wrapped label) has none. The commit then said "no clipped tab
   text" and "measured after: one row at 768" with no test at 768.
2. **A test that did not bite, caught only by mutation.** TC35-000009 first
   passed with the change listener removed, because the long pick was already
   the default. Fixed before commit by switching between two picks.
3. **A fix for a case the real code cannot produce.** The duplicate-key test
   stubbed the generator with a 60/40 vs 50/50 pair the generator never makes.
   I took the research table's wording ("only genre % differ") without
   reproducing the case. The rule is right; the claim that it fixed the
   measured near-duplicates was not.
4. **A measurement against the wrong state.** The first affinity timing read
   0 ms because the lab loads pair data only when the Genre tab opens. Caught
   by checking the result size (0 successful pairs), not the timing.
5. **A chained heredoc split an `&&` chain.** `git add` ran and the commit did
   not, leaving a half-staged index. Caught by reading `git status`.
6. **Several concerns per commit** (`aa364e3`) and two commits chained in one
   command (`bca61ea`, `46469d8`).

## Lessons

- Test the defect itself: for "stays on one line", count lines, not overflow.
- Before trusting a new test, reintroduce the defect and see it fail; when it
  stays green, find out why before going on.
- Reproduce a measured case with the real code before writing a fix for it.
  A stub may only produce states the real code can produce.
- Sanity-check a measurement's result size before its timing.
- Write the commit message to a file, commit as its own step, read
  `git show --stat`. Never put a heredoc inside an `&&` chain.
- One concern per commit, even when the concerns land together.
- Put the measuring command next to every number in a doc or commit message.
